# Benchmarking Approach

*How GreenCode measures execution time, resources and energy, why it is done this way, and what the literature says about doing it properly.*

## 1. What I am benchmarking, and what I am not

It is worth being precise about the question, because it determines the method. Industry tools such as pgbench, SysBench and HammerDB answer a *systems* question: how many transactions per second can this PostgreSQL installation sustain as concurrent clients are added, and where does latency break down [32], [33]. That tradition goes back to the Wisconsin benchmark of Bitton, DeWitt and Turbyfill [34], which first argued that database systems should be compared on a controlled, synthetic relation set rather than on anecdote.

GreenCode asks a narrower question. I am not comparing database engines or hardware; I am comparing two versions of the *same* query (or function) on the *same* engine and machine, and asking whether the rewrite is faster, cheaper in resources and lower in energy, with enough confidence to say so. That is a paired, single-client, steady-state micro-benchmark, and the right precedent for it is not TPC-C but the work on statistically rigorous performance evaluation by Georges, Buytaert and Eeckhout [21] and the cautionary paper by Mytkowicz et al. on how easily measurement setups produce wrong conclusions [22]. Where the standard tools do matter is in the practices they encode — warm-up, steady-state, a fixed dataset, a known machine — which I have carried across.

## 2. The controlled dataset

Every SQL case runs against one deterministic dataset, the `bench` schema (`customers` 50 000 rows, `products` 2 000, `orders` 200 000, `order_items` 600 000), generated by a seed script so that it is identical on every run and every machine. This is the same principle as pgbench's `-i` initialisation step and TPC-H's `dbgen` [35]: the data is part of the benchmark definition, not an incidental input. The shape of the data is deliberately modest. At this size the whole working set fits in PostgreSQL's shared buffers after warm-up, so I am measuring query execution rather than disk I/O, which is the right thing for a project about rewriting queries. Leis et al. showed that optimiser quality depends heavily on data skew and join structure [36], so the dataset includes correlated keys and realistic status and country distributions rather than uniform noise. Python cases carry their own workload in the case file (`setup` builds the data, `call` is the expression timed), which keeps the two halves of the project symmetric.

## 3. The measurement protocol

Each benchmark run follows the same steps, implemented in `benchmark/runner.py`, `benchmark/sql_runner.py` and the sandbox worker:

1. **Environment snapshot.** CPU model, core count, Python and PostgreSQL versions, operating system and every setting in force are stored with the run, so a result can always be traced back to the conditions that produced it [25].
2. **Warm-up.** Three untimed executions before any sample is recorded. For SQL this primes the buffer cache and plan cache, which is what the pgbench documentation and every practitioner guide insist on [32]; for Python it lets the interpreter settle and populates any lazily built state. Georges et al. call this reaching steady state and show that skipping it biases results towards the warm-up cost of whichever variant runs first [21].
3. **Repetitions.** Fifteen timed executions by default, thirty or more when energy is being measured, each timed with `perf_counter_ns`. The Python worker disables the garbage collector around each timed call and collects before it, so collection pauses are not attributed at random to one variant. Every sample is stored, not just a summary, so the distribution can be re-examined [22].
4. **Pairing and interleaving.** The original and the candidate are always benchmarked back to back within the same session, and the suite randomises case order with a fixed seed and alternates which condition runs first. This is the mitigation Mytkowicz et al. recommend for the slow drift (thermal state, background services) that otherwise confounds variant with time of day [22].
5. **Resource counters.** CPU time and peak working set from psutil; for SQL, the PostgreSQL backend process is identified and its CPU time and memory are read directly, and `EXPLAIN (ANALYZE, BUFFERS)` is captured once per variant so that planner cost, actual rows and shared-buffer hits are available alongside the timings. Buffer hits versus reads are exactly the "cache hit ratio" metric the practitioner literature stresses [32], and they let me check that a speed-up is a real reduction in work and not an artefact of caching.
6. **Energy.** The whole repetition loop is wrapped in an energy window read from the processor's RAPL counters through LibreHardwareMonitor [31], with a six-second idle baseline subtracted, following the measurement chain Bachras and Jacobsen use for database workloads [27] and the characterisation of RAPL's behaviour by Khan et al. [5]. Because the counter is machine-wide and refreshes about once a second, energy is only interpreted over the whole loop, never per execution, and the coefficient estimate of Lannelongue et al. [6] is always recorded alongside so measured and modelled figures can be compared.
7. **Time limits.** A statement timeout of 30 s for SQL and a sandbox timeout for Python turn a pathological rewrite into a recorded failure rather than a hung run.

## 4. Statistics

A single number is never reported on its own. For each variant I store the mean, median, standard deviation, coefficient of variation and a 95 % confidence interval (Student's *t*), and for each pair the speed-up as a ratio of medians, a two-sided Mann–Whitney *U* test, Cliff's δ as an effect size and whether the two confidence intervals overlap. Medians and non-parametric tests are used because benchmark timings are right-skewed and occasionally bimodal, so the mean and a *t*-test can be misleading [21], [37]. Across cases, speed-ups are combined with geometric means, because ratios are multiplicative, and the hypotheses are tested with paired Wilcoxon signed-rank tests on log ratios. I report the test both per-protocol (only cases verified under both conditions) and intention-to-treat (a rejected candidate scores no improvement), since the two answer different questions and can legitimately disagree.

## 5. Best practice I have adopted, and where I knowingly depart from it

The practitioner guidance for PostgreSQL benchmarking says: warm the cache, isolate the load generator from the server, keep the storage layout representative, and never trust TPS alone [32], [33]. I follow the first and the last. I depart from the second by necessity: the client, PostgreSQL, Ollama and the dashboard all run on one laptop, so the client's own overhead is present in every timing. Because that overhead is the same for both members of a pair, it cancels in the ratio, which is the quantity the hypotheses are about; it would not cancel in an absolute TPS figure, which is why I do not report one. The third does not apply, since the dataset is cache-resident by design.

Raasveldt et al.'s *Fair Benchmarking Considered Difficult* [38] lists the ways database comparisons go wrong — unequal warm-up, cold versus hot caches, different configurations, cherry-picked queries, and results reported without variance. Each of those has a specific countermeasure above: identical warm-up for both variants, hot cache for both, one configuration recorded in the snapshot, a fixed and published case set, and every sample retained. Kalibera and Jones [37] add that the number of repetitions should be chosen from the observed variance rather than guessed, which is why the coefficient of variation is stored and why the dashboard flags pairs whose confidence intervals overlap rather than declaring a winner.

Ferreira's TU Dublin dissertation [23] is a useful local warning: the same JavaScript benchmarks moved substantially when only the environment configuration changed. The environment snapshot, the single-machine rule and the paired design are my answer to that. A recent comparison of raw SQL against an ORM on PostgreSQL [39] measured CPU, memory and execution time across a fixed set of query patterns, which is close to my own design and reinforces that execution time alone is not a sufficient metric.

## 7. Precedents from theses and recent studies

I looked for prior work that benchmarks in the way I do, with a preference for Irish theses. Yang's DCU doctoral thesis [40] is the closest Irish precedent on method: it argues that benchmark results are only comparable when the features being measured are fixed and declared in advance, and builds an explicit evaluation methodology around that, which is the same reasoning behind GreenCode's fixed rule catalogue, fixed dataset and stored environment snapshot. Together with Ferreira's TU Dublin dissertation on environment sensitivity [23] and Connolly Bree's UCD thesis on design-level energy effects [4], it forms the Irish strand of this work; I did not find a recent Irish thesis that benchmarks PostgreSQL query rewrites specifically, so the closer precedents are international.

The most directly comparable is Cedeño et al. [41], who ran the 22 TPC-H queries on PostgreSQL and measured per-query energy on both client and server while applying optimisation strategies (indexing and compression), finding that indexing cut energy on most queries. Taipalus [42] measured PostgreSQL 16 throughput with pgbench and whole-system power under different logical designs, repeating each run three times from a cold reboot, and found normalisation changed energy per transaction by around 74 % — a reminder that schema and query shape, not only hardware, drive the energy figure. The question behind my H4 was asked directly by Niemann et al. [43], who ran TPC-H and the Star Schema Benchmark on PostgreSQL and concluded that faster queries generally did use less energy, and earlier by Tsirogiannis, Harizopoulos and Shah [44], whose SIGMOD study found that within a single server "the most energy-efficient configuration is typically the highest-performing one". GreenCode tests that claim at the level of individual rewrites rather than whole workloads, and the intention-to-treat analysis is where it would show up if the claim fails for AI-generated code. Mahajan, Blakeney and Zong [45] measured query-level energy on MySQL, MongoDB and Cassandra with YCSB and showed that query-level optimisations alone saved energy without costing throughput, which is the premise my SQL half depends on.

Two further studies shaped how I report numbers. Salunke and Ouda [46] built a small Python harness to compare PostgreSQL and MySQL, ran each query a hundred times and reported medians and percentiles rather than means — the same choice I make, for the same reason. Lindblom and Strandin's Lund master's thesis [47] is a good example of pgbench done carefully (separate client machine, hour-long runs repeated several times, one variable changed at a time) and also of why that style does not fit here: their effect sizes were fractions of a percent and needed long runs to resolve, whereas a query rewrite typically changes execution time by an order of magnitude and is better resolved by many short paired repetitions.

## 8. Limitations I will report

Single machine, single client, single PostgreSQL version; a cache-resident dataset that does not exercise I/O; one-second energy granularity that is coarse relative to millisecond queries; and a benchmark set I wrote myself, which is representative of the rule catalogue rather than of production workloads. None of these invalidate a paired comparison on the same machine, but all of them limit how far the absolute numbers generalise, and they are stated in the threats-to-validity section of the methodology.
